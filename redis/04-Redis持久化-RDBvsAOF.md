# 04 深入:RDB vs AOF 对比与选型

- **日期**:2026-08-27
- **一句话总结**:Redis 是内存数据库,断电就全没了,持久化是把内存数据"落到磁盘"的两套机制——RDB 是"定时拍照",AOF 是"记账日志"。面试必问对比,本文讲透原理 + 选型 + 常见坑。
- **配套代码**:无需代码,本文是纯原理 + 配置篇,配置示例可直接复制。

---

## 1. 为什么需要持久化

Redis 数据全在内存,速度快是快,但**一断电/宕机,内存数据全丢**。

> 缓存丢了无所谓(重新查库回填),但**库存、订单号、点赞数、登录态**这些要是也丢,业务就出事故了。
> 所以要把数据"另存一份"到磁盘,重启后能恢复。

Redis 提供两种持久化机制(可以只用一种,也可以同时用):

| | RDB (Redis DataBase) | AOF (Append Only File) |
|---|---|---|
| **大白话** | **定时拍照**:每隔一段时间把内存数据"拍一张快照"存进文件 | **记账日志**:每执行一条写命令,都追加记到日志文件里 |
| **文件** | `dump.rdb`(二进制,紧凑) | `appendonly.aof`(文本,可读) |
| **恢复速度** | 快(直接加载二进制) | 慢(要重放所有写命令) |
| **数据丢失** | 可能丢一个快照周期(比如 5 分钟) | 最多丢 1 秒(按配置) |
| **对性能影响** | fork 子进程做快照,主进程几乎不卡 | 每秒刷盘,基本无感;每毫秒刷盘略影响 |
| **适合** | 追求恢复速度、能容忍丢几分钟数据 | 追求不丢数据(缓存/计数/订单类) |

## 2. RDB:定时拍照

### 2.1 原理

`SAVE` / `BGSAVE` 把内存数据写成二进制快照文件。**生产必须用 `BGSAVE`**(Background,后台):主进程 `fork` 出一个子进程,子进程负责写文件,主进程继续服务请求,不阻塞。

```bash
# 手动触发(生产用这个,后台执行不阻塞)
127.0.0.1:6379> BGSAVE

# 阻塞式触发(会卡住 Redis,生产禁用!只用于测试理解)
127.0.0.1:6379> SAVE
```

### 2.2 自动触发条件(redis.conf)

```conf
# 900 秒内至少有 1 个 key 变化 → 快照
save 900 1
# 300 秒内至少有 10 个 key 变化 → 快照
save 300 10
# 60 秒内至少有 10000 个 key 变化 → 快照
save 60 10000
```

### 2.3 缺点(为什么"丢数据")

快照是**周期性**的,不是实时的。`save 900 1` 意味着"最多 15 分钟才拍一次"。如果 Redis 在第 5 分钟宕机,这 5 分钟内的所有写入**全丢**。

> 适用:可容忍丢数据的场景(纯缓存、热搜榜等),或作为 AOF 的补充。

## 3. AOF:记账日志

### 3.1 原理

每执行一条**写命令**(set/hset/incr...),Redis 就把它追加到 `appendonly.aof` 文件末尾。恢复时把日志里的命令**从头到尾重放一遍**,数据就回来了。

```
# appendonly.aof 内容(人类可读的命令记录)
*3
$3
SET
$5
stock
$3
100
```

### 3.2 三种刷盘策略(核心考点)

| 配置 `appendfsync` | 行为 | 丢数据 | 性能 |
|---|---|---|---|
| `always` | 每执行一条写命令就刷盘 | **一条都不丢** | 最慢(每条都磁盘 IO) |
| `everysec` | 每秒批量刷一次 | **最多丢 1 秒** | 快(默认推荐) |
| `no` | 交给操作系统决定何时刷 | 可能丢较多 | 最快(不推荐,失去持久化意义) |

```conf
appendonly yes          # 开启 AOF(Redis 7 之前默认关,7.0+ 默认开)
appendfilename "appendonly.aof"
appendfsync everysec    # 默认:每秒刷盘,最多丢 1 秒
```

### 3.3 AOF 的两个进阶机制(面试加分)

**① AOF 重写(BGREWRITEAOF)——解决文件无限膨胀**

日志一直追加会越来越大(比如一个 key 被 set 了 1 万次,日志里有 1 万条命令,其实只需要最后一条)。**重写**= 把当前内存数据生成"最少命令集"的新日志,替换旧文件。

```bash
127.0.0.1:6379> BGREWRITEAOF   # 手动触发,后台执行
```

自动触发条件:

```conf
auto-aof-rewrite-percentage 100   # 文件比上次重写时增长 100% 触发
auto-aof-rewrite-min-size 64mb    # 文件至少 64MB 才触发
```

**② AOF 文件损坏怎么办(redis-check-aof)**

AOF 是文本追加,宕机可能写坏最后几条记录。启动时 Redis 检测到损坏会拒绝启动,用自带工具修复:

```bash
# 修复 aof 文件(会丢弃损坏的尾部数据)
redis-check-aof --fix appendonly.aof
```

## 4. RDB + AOF 混合:生产标准配置

**只用 RDB**:丢数据多;只用 AOF:恢复慢、文件大。**最佳实践:两个都开,各取所长**:

| 角色 | 用谁 | 为什么 |
|---|---|---|
| **恢复数据** | AOF 优先 | 丢得少(最多 1 秒) |
| **兜底/备份** | RDB | 文件小、恢复快,适合定期备份到云存储 |
| **快速启动** | 冷启动先加载 RDB | 比重放 AOF 快得多 |

```conf
# 两个都开
save 900 1
save 300 10
appendonly yes
appendfsync everysec
```

**Redis 4.0+ 的混合持久化**(`aof-use-rdb-preamble yes`):
AOF 重写时,文件头部直接放一段 **RDB 二进制快照**(把当前数据全量拍进去),后面再追加新命令。恢复时:先秒载 RDB 部分,再重放少量 AOF 部分——**既快又不丢**。这是当前版本的默认行为。

> 面试口径:混合持久化 = AOF 文件里"RDB 打底 + 增量命令追加",兼顾 RDB 的恢复速度和 AOF 的低丢失,是 Redis 4.0+ 的推荐方案。

## 5. 选型决策表(面试直接背)

| 场景 | 选型 | 理由 |
|---|---|---|
| 纯缓存,丢了可重新查库 | RDB 或都不开 | 恢复快,丢了无所谓 |
| 计数/库存/订单,不能丢 | AOF(`everysec`)或混合 | 最多丢 1 秒 |
| 大数据量冷启动 | 混合持久化 | RDB 部分秒载,不用重放全部日志 |
| 主从架构 | 主库开 AOF,从库可只开 RDB | 主库保证不丢,从库负责恢复速度 |
| 追求极致性能,数据可丢 | 全关 | 快,但宕机全丢(仅测试/纯缓存) |

**一句话选型口诀**:能丢数据用 RDB,不能丢用 AOF,**生产默认混合(两个都开)**。

## 6. 踩坑提醒

1. **`SAVE` 会阻塞主进程**:大内存时执行 SAVE,Redis 会卡住几秒到几十秒,线上等于事故。一律用 `BGSAVE` / `BGREWRITEAOF`。
2. **RDB 触发条件别设太频繁**:`save 60 10000` 意味着 1 分钟 1 万次写入就拍快照,fork 子进程有内存开销,大实例频繁 fork 有风险。
3. **AOF 刷盘别用 `always`**:每条命令都刷盘,写性能可能掉一半;默认 `everysec` 够用。
4. **fork 的写时复制(COW)**:BGSAVE 时主进程内存变化会复制一份,瞬间内存占用会翻倍,大实例注意内存余量。
5. **AOF 重写别手动频繁触发**:重写本身也吃资源,交给自动触发即可。
6. **备份要异地**:RDB 文件定期 `scp`/上传对象存储,别和 Redis 在同一台机器(机器挂了备份也没了)。

## 7. 面试高频追问

**Q: RDB 和 AOF 各有什么优缺点?**
A: RDB 二进制文件小、恢复快,但快照是周期性的,最多丢一个周期(几分钟)的数据;AOF 记录每一条写命令,`everysec` 最多丢 1 秒,恢复时重放命令较慢,文件会膨胀需要重写。

**Q: 为什么 BGSAVE 不阻塞?**
A: fork 子进程,子进程把内存数据写成文件,主进程继续处理请求。fork 用的是写时复制(COW),子进程读到的是 fork 那一刻的内存快照,期间主进程修改的数据页会复制,不影响一致性。

**Q: 两个都开,重启时用哪个恢复?**
A: 优先用 AOF(丢得少);Redis 4.0+ 混合持久化时,AOF 文件头部是 RDB 快照,先秒载 RDB 再重放少量命令,又快又不丢。

**Q: AOF 文件一直变大怎么办?**
A: 触发 AOF 重写(BGREWRITEAOF),把当前内存数据压缩成最少命令集;自动触发条件看增长百分比和最小大小,也可以手动执行。

**Q: 只开 RDB,宕机会丢多少数据?**
A: 最多丢最近一次成功快照到宕机之间的所有写入。比如 `save 900 1`(15 分钟没写入就不拍),刚写完 10 分钟的数据可能全丢。所以不能丢数据的场景必须开 AOF。
