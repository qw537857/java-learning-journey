# 02 深入:缓存穿透 / 击穿 / 雪崩(方案对比与落地)

- **日期**:2026-08-27
- **一句话总结**:面试必考的"缓存三兄弟"——穿透是"查了不存在的数据",击穿是"热点 key 过期瞬间被打爆",雪崩是"大量 key 同时过期"。三种问题的解法完全不同,本文给全代码级方案。
- **配套代码**:可运行示例在 [redis-demo](./redis-demo/) 的 `CacheService` 与 `BloomFilterService`。

---

## 1. 先分清三兄弟(一图流)

| | 穿透 (Penetrate) | 击穿 (Breakdown) | 雪崩 (Avalanche) |
|---|---|---|---|
| **现象** | 请求的数据**根本不存在**,缓存和数据库都没有 | 一个**热点 key 刚好过期**,大量请求同时打到 DB | **大量 key 同一时间过期**,一大批请求同时打到 DB |
| **坏在哪** | 恶意/异常请求绕过缓存直接打库,DB 扛不住 | 单点热点被打爆,DB 压力瞬间拉满 | 大面积缓存失效,DB 被整体打垮 |
| **典型场景** | 攻击者遍历不存在的 id 查询 | 秒杀商品详情、爆款文章 | 缓存设置了相同的固定过期时间(比如全部 10 分钟) |
| **关键区别** | 数据**没有**(空数据) | 数据**有**,但 key 临时**没了** | 数据**有**,但一大批 key **同时没了** |

> **记忆口诀**:穿透=查不存在;击穿=单个热点过期;雪崩=大面积同时过期。
> 面试先把这三个定义说清楚,基本就赢了一半。

## 2. 穿透:缓存空值 + 布隆过滤器

### 2.1 解法一:缓存空值(最简单,先上这个)

查不到数据时,把"空"也缓存起来,短过期。下次同样的请求直接命中空缓存,不打库。

```java
// 伪代码核心:查不到也 set 一个空串,60 秒过期
public String getArticle(Long id) {
    String key = "cache:article:" + id;
    String v = redis.opsForValue().get(key);
    if (v != null) {
        return v.isEmpty() ? null : v;   // 命中空缓存,直接返回 null
    }
    String fromDb = queryDb(id);
    if (fromDb == null) {
        redis.opsForValue().set(key, "", 60, TimeUnit.SECONDS); // 缓存空值
        return null;
    }
    redis.opsForValue().set(key, fromDb, 300, TimeUnit.SECONDS);
    return fromDb;
}
```

**优点**:实现简单,一行就堵住重复穿透。
**缺点**:① 空 key 会堆积(攻击者造 100 万个不存在的 id,就多 100 万个空 key);② 只能挡住"同一个不存在的 key"的重复请求,挡不住"不断换新 id"的攻击。

### 2.2 解法二:布隆过滤器(挡"换着 id 打"的攻击)

**布隆过滤器是什么(大白话)**:一个很省内存的"名单"。把**所有合法存在的 id** 提前放进去,查询前先问它:"这个 id 在名单里吗?"
- 它说**不在** → 100% 不在,直接返回,连 Redis 都不用查。
- 它说**在** → 可能在(有极小概率误判),继续走正常缓存流程。

它用多个 hash 函数把 id 映射到位数组的几个 bit 上,所以**一个亿的 id 也就几百 MB 内存**,比存所有 key 省太多。

```java
// 手写一个最简布隆过滤器(理解原理用;生产直接用 Guava/Redisson 的)
public class SimpleBloomFilter {

    private final BitSet bits = new BitSet(1 << 20); // 100 万 bit 位
    private static final int[] SEEDS = {3, 7, 11, 13, 31}; // 5 个 hash 种子

    public void add(String value) {
        for (int seed : SEEDS) {
            int h = (value.hashCode() * seed) & (bits.size() - 1);
            bits.set(h);
        }
    }

    public boolean mightContain(String value) {
        for (int seed : SEEDS) {
            int h = (value.hashCode() * seed) & (bits.size() - 1);
            if (!bits.get(h)) {
                return false; // 任何一个位是 0,肯定不在
            }
        }
        return true; // 全为 1,可能在里面(误判率≈1%)
    }
}
```

**生产用法(Guava,一行搞定)**:

```xml
<dependency>
    <groupId>com.google.guava</groupId>
    <artifactId>guava</artifactId>
    <version>32.1.3-jre</version>
</dependency>
```

```java
import com.google.common.hash.BloomFilter;
import com.google.common.hash.Funnels;
import java.nio.charset.StandardCharsets;

// 预计放 100 万条,允许 1% 误判
BloomFilter<String> bloom = BloomFilter.create(
        Funnels.stringFunnel(StandardCharsets.UTF_8), 1_000_000, 0.01);

// 启动时:把所有存在的 id 灌进去
bloom.put("1001");
bloom.put("1002");

// 查询时:先过布隆
public String getArticle(Long id) {
    if (!bloom.mightContain(String.valueOf(id))) {
        return null;                 // 肯定不存在,直接短路,连 Redis 都不查
    }
    // 走正常缓存逻辑...
    return null;
}
```

**什么时候用布隆**:数据量大、key 总量可控(比如商品/用户总数是已知量级)、且能容忍"极少误判去查一次库"。数据总量无限增长的场景(日志、流水号)不太适合。

> **面试口径**:穿透先答"缓存空值 + 布隆过滤器"两个方案,再说空值方案简单但防不住换 id 攻击,布隆过滤器省内存能挡住——**两个都要答,只答一个会被追问**。

## 3. 击穿:互斥锁重建缓存(重点代码)

### 3.1 问题复现

热点 key(比如爆款商品详情)过期的一瞬间,1000 个请求同时发现缓存没有 → 1000 个请求同时查库 → DB 被打爆。

### 3.2 解法:互斥锁,只让一个线程去查库

核心思想:**缓存没有时,先抢锁,抢到锁的人才准查库重建缓存;其他人等锁或直接返回旧值**。

```java
// 完整版:互斥锁重建缓存(双重检查)
public String getArticleWithLock(Long articleId) {
    String key = "cache:article:" + articleId;
    String lockKey = "lock:article:" + articleId;
    String requestId = UUID.randomUUID().toString(); // 锁的"身份证"

    // 第一次查缓存
    String cached = redis.opsForValue().get(key);
    if (cached != null) {
        return cached;
    }

    // 没命中 → 抢锁(SET NX EX,原子操作)
    Boolean locked = redis.opsForValue()
            .setIfAbsent(lockKey, requestId, 3, TimeUnit.SECONDS);
    if (Boolean.TRUE.equals(locked)) {
        try {
            // 双重检查:可能上一个线程刚重建完,别重复查库
            cached = redis.opsForValue().get(key);
            if (cached != null) {
                return cached;
            }
            String fromDb = queryDb(articleId);   // 只有一个线程进来查库
            redis.opsForValue().set(key, fromDb, 300, TimeUnit.SECONDS);
            return fromDb;
        } finally {
            // 释放锁:用 Lua 保证"只有自己(比对 requestId)才能删",防止误删别人的锁
            releaseLock(lockKey, requestId);
        }
    }

    // 没抢到锁:说明别的线程正在重建,先返回一个"降级"值(旧缓存/默认值)
    // 生产上这里可以返回上一次的旧缓存(双缓存)或稍等重试
    return getStaleCache(articleId);
}

/** 释放锁:先比对 requestId 再删,防止把别人的锁删了(经典坑) */
private void releaseLock(String lockKey, String requestId) {
    String lua = "if redis.call('get', KEYS[1]) == ARGV[1] " +
                 "then return redis.call('del', KEYS[1]) " +
                 "else return 0 end";
    redis.execute(new DefaultRedisScript<>(lua, Long.class),
            Collections.singletonList(lockKey), requestId);
}
```

**三个关键点(面试会追问)**:
1. **为什么要双重检查?** 抢到锁后可能上一个线程刚重建完缓存,再查一次能省一次查库。
2. **为什么锁要带 requestId + Lua 删?** 锁 3 秒自动过期后,如果 A 线程还没执行完,B 线程抢到了锁;这时 A 执行完直接 `del` 会把 B 的锁删掉。用"比对身份再删"的 Lua 脚本解决。
3. **没抢到锁怎么办?** 别傻等,返回降级数据(旧缓存)或短暂重试,保证接口不挂。

### 3.3 另一种思路:逻辑过期(热点数据永久不过期)

缓存**不设物理过期时间**,而是在 value 里塞一个逻辑过期时间戳。读的时候发现"逻辑上过期了",**先返回旧数据给用户**,同时后台起一个线程去重建缓存。

```java
// value 存:数据 + 逻辑过期时间
String value = fromDb + "|" + (System.currentTimeMillis() + 300_000);
redis.opsForValue().set(key, value);   // 不设过期时间,物理上永不过期

// 读的时候:
String v = redis.opsForValue().get(key);
long logicExpire = Long.parseLong(v.split("\\|")[1]);
if (System.currentTimeMillis() < logicExpire) {
    return v.split("\\|")[0];          // 没过期,直接返回
}
// 逻辑过期了:先返回旧数据,再异步重建缓存(配合互斥锁防止重复重建)
```

**优点**:用户永远拿得到数据,不等待;适合"数据旧一点没关系"的场景。
**缺点**:数据一致性弱(过期后仍返回旧值),实现比互斥锁复杂。

> **面试口径**:击穿答"互斥锁重建缓存(双重检查 + Lua 释放)"为主方案,再补一句"热点数据也可以用逻辑过期,先返回旧值再异步重建"。

## 4. 雪崩:过期时间加随机值 + 多级缓存

### 4.1 问题复现

如果所有缓存都设 `set(key, value, 3600)` —— 整点一到,几万个 key 同时过期,所有请求同时打到 DB。

### 4.2 解法一:过期时间加随机值(最常用,先答这个)

```java
// 基础过期时间 300 秒,再加 0~60 秒随机,让过期时间错开
long expire = 300 + new Random().nextInt(60);
redis.opsForValue().set(key, value, expire, TimeUnit.SECONDS);
```

**原理**:大家不再"同时"过期,而是分散在 5 分钟窗口内,DB 压力被摊平。

### 4.3 解法二:多级缓存(本地缓存 + Redis)

Redis 前面再挡一层**本地缓存**(Caffeine/Guava Cache)。即使 Redis 大面积失效,请求先打到本地缓存,只有本地也没有才去 Redis/DB。

```java
// Caffeine 本地缓存(进程内,毫秒级访问)
Cache<String, String> localCache = Caffeine.newBuilder()
        .maximumSize(10_000)            // 最多 1 万个
        .expireAfterWrite(60, TimeUnit.SECONDS) // 本地 60 秒过期
        .build();

public String getArticleWithLocal(Long id) {
    String key = "cache:article:" + id;
    String v = localCache.getIfPresent(key);   // 1. 先查本地
    if (v != null) return v;
    v = redis.opsForValue().get(key);          // 2. 再查 Redis
    if (v != null) {
        localCache.put(key, v);                // 回填本地
        return v;
    }
    String fromDb = queryDb(id);               // 3. 最后查库
    localCache.put(key, fromDb);
    redis.opsForValue().set(key, fromDb, 300 + new Random().nextInt(60), TimeUnit.SECONDS);
    return fromDb;
}
```

### 4.4 解法三:高可用兜底(Redis 集群 + 熔断降级)

- Redis 用**集群/哨兵**,别单点;Redis 真挂了,接口走**降级**(返回兜底数据/限流),不让 DB 被打死。

> **面试口径**:雪崩答三件套——① 过期时间加随机值;② 多级缓存(本地缓存挡一层);③ Redis 高可用 + 熔断降级兜底。这三层按"防→挡→兜"的顺序讲,层次感拉满。

## 5. 三兄弟对比速查表(背这个就够面试)

| 问题 | 一句话定义 | 首选方案 | 进阶方案 |
|------|-----------|---------|---------|
| 穿透 | 查**不存在**的数据 | 缓存空值 | 布隆过滤器(挡换 id 攻击) |
| 击穿 | **单个热点** key 过期瞬间 | 互斥锁重建缓存 | 逻辑过期 + 异步重建 |
| 雪崩 | **大量 key 同时**过期 | 过期时间加随机值 | 多级缓存 / 集群降级 |

## 6. 踩坑提醒

1. **布隆过滤器只能"挡不存在",不能"拦真实数据"**:误判会让个别不存在请求穿透到 DB,所以布隆要配合缓存空值一起用,双保险。
2. **互斥锁必须带 requestId 比对再删**:不带比对,慢线程会误删快线程的锁,出现"锁失效"。
3. **锁的过期时间要大于重建缓存的最坏耗时**:重建要 3 秒,锁设 1 秒,第一个线程没建完锁就没了,后面全挤进来。
4. **空值缓存的过期时间别太长**:60 秒合适,太长会导致"刚新增的数据"长时间查不到(因为缓存了空)。
5. **本地缓存注意一致性**:进程内缓存会有短暂脏读,写操作多的数据慎用;改了数据要主动清本地缓存。
6. **雪崩的随机值别只加在"写缓存"处**:如果所有 key 都是启动时批量灌的,启动时也要加随机值。

## 7. 面试高频追问

**Q: 布隆过滤器为什么省内存?**
A: 不存完整 id,只存 id 经过多个 hash 函数映射出的几个 bit 位,一个 id 只占几个 bit,亿级数据也就几百 MB;代价是有误判率(可能把不存在的误判为存在,不会把存在的判为不存在)。

**Q: 布隆过滤器能删除吗?**
A: 标准布隆不支持删除(一个 bit 可能被多个元素共享,置 0 会误伤)。要支持删除用**计数布隆过滤器(CBF)**或换 **Redis 的 Cuckoo Filter**。

**Q: 击穿的互斥锁和分布式锁是同一个东西吗?**
A: 是同一套思路(SET NX EX + Lua),击穿场景是"缓存重建锁",锁的粒度是 key 维度;下一篇 03 会讲完整的分布式锁演进。

**Q: 穿透和击穿怎么区分?**
A: 穿透是数据**不存在**(空数据打库);击穿是数据**存在但缓存刚好过期**(单 key 瞬间打库)。一个堵"空",一个堵"过期瞬间"。
