# 01 MySQL 高可用:主从复制与集群演进

- **日期**:2026-08-31
- **一句话总结**:从"一台 MySQL 单打独斗"演进到"一主多从 + 自动切换",解决的是**不让数据库成为单点故障**这件事。本篇用商城订单系统串起**主从复制原理、同步方式、集群架构、高可用切换**四大块,面试高频题全覆盖。
- **配套代码**:文末含 binlog 排查命令、主从配置示例(占位符)。

## 零、贯穿案例先立住:一个商城订单系统

想象你在做**电商系统**,核心库是一台 MySQL(单机),里面有一张 **`order` 订单表**(假设 1000 万行)。

单机的日子很美好:连接数据库、CRUD,一次搞定。但某天你发现:

1. 凌晨 3 点,**这台 MySQL 挂了** → 全站报错,用户下不了单 → 一晚上损失惨重。
2. 就算没挂,**促销活动**一到,读请求(查订单、查商品)暴涨,数据库 CPU 打满 → 查询越来越慢。
3. 表数据越来越多,**单表查询越来越慢**,加了多少索引都不够。

于是你意识到:**一台库撑不住一个想长大的系统**。MySQL 的高可用、主从、集群,就是为这些场景设计的。下面逐个拆。

---

## 一、什么是高可用(HA),为什么必须做

**大白话**:高可用 = **让系统尽量不因为某台机器挂了而整体趴窝**。衡量指标叫 **SLA**,常说"几个 9"。

| 几个 9 | 每年允许停机 | 大白话 |
|--------|-------------|--------|
| 99.9%(三个9) | 约 8.7 小时 | 普通业务 |
| 99.99%(四个9) | 约 52.6 分钟 | 电商核心 |
| 99.999%(五个9) | 约 5.3 分钟 | 金融、支付 |

**面试必问:为什么单机做不到高可用?**
单机 = **单点故障(Single Point of Failure, SPOF)**。机器坏了、磁盘坏了、系统升级、机房断电,任何一个都会让数据库不可用,而 SLA 直接归零。高可用的本质就是**消除单点**——让数据库有"备胎",主的不行备的上。

> **核心心法(背下来)**:高可用不是"让机器不坏",而是"**坏了也能很快恢复、业务不断**"。手段千千万,本质都是:**冗余(多准备几台)+ 自动切换(坏了自动顶上)+ 快速恢复**。

## 二、主从复制(Master-Slave Replication):高可用的地基

### 2.1 是什么

**大白话**:准备两台 MySQL,一台叫**主库(Master)**只负责写,一台叫**从库(Slave)**自动把主库的变更复制过来,负责读。数据两边一模一样,主库挂了从库能顶上。

```
Master(可写可读,一般只写)  ──推送 binlog──►  Slave(只读,扛读流量)
```

### 2.2 核心原理:binlog + 三个线程(面试必考)

这条链路是 MySQL 面试题里的"铁饭碗",必须能默写:

```
主库写操作
   │
   ▼
主库 binlog(二进制日志,记录所有变更)
   │ 主库 IO 线程:binlog → 发送给从库
   ▼
从库:
   ├─ IO 线程:接收主库 binlog,写入本地 relay log(中继日志)
   └─ SQL 线程:读 relay log → 在从库重放(执行) → 数据跟上
```

三个线程名字一定要记住:

| 线程 | 在哪 | 干什么 |
|------|------|--------|
| **dump 线程(转储)** | 主库 | 把 binlog 日志推给从库的 IO 线程 |
| **IO 线程** | 从库 | 接收日志,写成 **relay log(中继日志)** |
| **SQL 线程** | 从库 | 读 relay log 并执行,真正把数据写到从库 |

**延伸考点:binlog 到底记录什么?**
binlog 不是"数据快照",是**每次数据变更的日志**(追加写)。所以从库靠"重放这份日志"就能追上主库。这也是后面**备份恢复、Canal、数据同步**的根基——上一篇 Canal 就是"伪装成从库读 binlog"。

### 2.3 三种复制模式(面试爱问一致性)

| 模式 | 大白话 | 数据丢失风险 | 常用吗 |
|------|--------|-------------|--------|
| **异步复制**(默认) | 主库写完 binlog 就算完事,不等从库 | 主库突然挂了,binlog 没发出去的变更会丢 | 最常用,性能最好 |
| **半同步复制** | 主库必须等"至少一个从库确认收到"才返回 | 大幅降低丢失,但主库要等,略慢 | 高可用常用 |
| **全同步复制**(组复制 MGR) | 主库等所有从库都确认才返回 | 几乎不丢,但最慢 | 强一致场景 |

> **面试金句**:方案没有绝对好坏,是"**一致性 vs 性能**"的取舍。要快就异步,要稳就半同步/全同步。订单要钱,宁可慢一点也不能丢。

### 2.4 主从怎么配(命令示意,占位符)

```sql
-- 主库:开 binlog(my.cnf)
[mysqld]
log-bin=mysql-bin          -- 开启二进制日志
server-id=1                -- 全局唯一,不能和从库重复
binlog_format=ROW          -- ROW 格式更安全,推荐

-- 从库:配置(my.cnf)
[mysqld]
server-id=2                -- 和主库不同即可
relay-log=relay-bin

-- 从库执行:建立复制关系(主库地址用占位符)
CHANGE MASTER TO
  MASTER_HOST='your-master-host',
  MASTER_USER='replica_user',
  MASTER_PASSWORD='your-pass',
  MASTER_LOG_FILE='mysql-bin.000001',
  MASTER_LOG_POS=0;
START SLAVE;

-- 检查从库状态(两个一定要是 Yes)
SHOW SLAVE STATUS\G
-- Slave_IO_Running: Yes
-- Slave_SQL_Running: Yes
```

> ⚠️ 实际配置注意:生产一般用 **GTID(全局事务标识)** 代替传统 file/position 定位,自动跳过重复事务,切换更方便。这里不展开,知道有这个东西、面试能提一嘴即可。

## 三、读写分离:把读流量从主库卸下来

### 3.1 为什么需要(面试必问)

上完主从,主库还是只写不读太浪费。图的是:**读多写少**是业务常态**(尤其是商城:下单的人少,看商品/看订单的人多)**。把读请求都打到从库,主库专注写,性能立刻不一样。

```
        ┌──────── Master(写) ──► 订单落库
用户的 ─┤
        └──────── Slave1(读) ─► 查订单
                 Slave2(读) ─► 查商品
```

### 3.2 怎么实现(三种主流方式)

| 方式 | 大白话 | 优点 | 缺点/适用 |
|------|--------|------|-----------|
| **中间件**(ShardingSphere / MyCat) | 程序连中间件,中间件自动把读写分流 | 对业务代码透明,好维护 | 多一层网络跳转 |
| **应用层路由**(多数据源 + AOP) | 代码里按方法注解决定走主还是走从 | 灵活 | 侵入代码,规则要自己写 |
| **框架内置**(如 Spring 动态数据源) | 封装好读写切换 | 简单 | 复杂规则难覆盖 |

### 3.3 最大隐患:主从延迟(面试送命题)

**问题**:主库写完了,从库还没来得及复制,这边立刻查从库发现"查不到刚下的单" → 用户刚下单就看不到。这叫 **主从延迟**。

**六大解决/缓解思路(背熟)**:

1. **强制读主**:对一致性要求极高的操作(订单支付成功后的回显),直接查主库。
2. **延迟感知**:记录"最近一次写库时间",读的时候如果从库延迟超过阈值就切主。
3. **半同步/串行复制**:减少复制延迟的根源。
4. **避免大事务/大表 DDL**:大事务会卡住复制,拆小。
5. **降低从库压力**:从库别干重活(别做复杂聚合),减少延迟。
6. **读写分离策略细化**:刚写完的 key 短暂标记"读主",过一会再走从。

> **面试答法模板**:先承认"主从延迟是读写分离绕不开的坑",再讲"对实时性敏感的操作强读主",最后补充"监控从库延迟(SHOW SLAVE STATUS 里的 Seconds_Behind_Master),超过阈值报警/切换"。

## 四、一主多从 / 集群:从单主到多主的演进

### 4.1 层级主从(树状)

从库下面还能挂从库,像公司组织架构。作用:**

1. **分摊复制压力**(从库的从库不直接连主库)
2. 更灵活地做"某个从库专供报表/数据分析"

```
Master
  ├─ Slave1
  │    └─ Slave1-1(报表专用)
  └─ Slave2
```

### 4.2 多主 / 主主复制(Master-Master)

两台都能写、互相复制。**注意**:双写容易冲突(两边同时改同一条),实战一半不这么干,更多是**互为主备**或配合业务拆分。

### 4.3 集群 / 高可用架构(重点)

集群 = 多台机器协同,关键能力是**主库挂了自动切换(故障转移, failover)**。

| 方案 | 大白话 | 切换方式 | 特点 |
|------|--------|---------|------|
| **Keepalived + 虚拟IP(VIP)** | 配一个虚拟 IP,主挂了 VIP 自动漂移到备机 | 秒级自动漂移 | 简单经典,但脑裂需注意 |
| **MHA(Master High Availability)** | 老牌故障切换组件,自动提从为主 | 数十秒 | 成熟,需有从库 |
| **Orchestrator** | 拓扑管理+自动切换,可视化 | 秒级 | 目前社区主流 |
| **MGR(MySQL Group Replication 组复制)** | MySQL 原生**多主**集群,自动选举 | 自动 | 原生,强一致;配合 MySQL Shell/InnoDB Cluster 使用 |

> **面试提分点**:"集群"不等于"高可用"——集群是**多机协作的形态**,高可用是这个形态**要达到的目标**。中间件(比如 **InnoDB Cluster = MGR + MySQL Shell + Router**)就是在努力把这些整合成"傻瓜式高可用"。

**脑裂(Split Brain)是什么(加分项)**
主备都有节点,网络断了导致两边都以为自己是主、都在写 → 数据不一致。对策:**仲裁节点/多数派投票(quorum)**、**fencing(隔离旧主)**。面试能说出"脑裂 + quorum 投票"这几个词,直接拉开差距。

## 五、高可用切换的心智模型(收尾必记)

把整个 MySQL 高可用浓缩成一个"三步走",面试讲起来又清晰又完整:

1. **冗余**:多台数据库(主从/集群),消灭单点 —— 这是**前提**。
2. **感知**:监控发现主库挂了(心跳检测、监控组件)。
3. **切换**:自动把流量切到备库 VIP 漂移 / 提升从库 -- 并**做 fencing 防止旧主复活捣乱**。

> **一句话总结全篇**:高可用不是某一种技术,是"**冗余 + 自动切换 + 快速恢复**"这套思路;主从复制是它的地基,读写分离和分库分表是它之上的性能手段,下一篇讲备份恢复,把"数据丢了怎么办"补上。

## 六、常见问题速查(面试突击)

| 问题 | 一句话答法 |
|------|-----------|
| 为什么主从复制要三个线程? | dump/IO/SQL 三线程,日志中转+重放,解耦收发 |
| binlog 和 relay log 啥区别? | binlog 在主库产生;relay log 是从库的中转日志 |
| 异步/半同步/同步区别? | 等多少个从库确认,一致性和性能的取舍 |
| 主从延迟怎么解决? | 强读主 + 监控延迟 + 避免大事务,多管齐下 |
| 高可用核心思想? | 冗余 + 自动切换 + 快速恢复 |
| 什么是脑裂? | 网络分裂导致双主,用 quorum/fencing 解决 |
