# 03 MySQL 读写分离与分库分表

- **日期**:2026-08-31
- **一句话总结**:读写分离把"读"和"写"拆到不同库,分库分表在数据量大到单表撑不住时"把数据拆开"。本篇用商城订单系统讲清楚**什么时候该用、怎么拆、中间件怎么配、拆完有哪些大坑**,全篇面试+实战双视角。
- **配套代码**:文末含 ShardingSphere 读写分离 + 分库分表配置示例(yaml,占位符,可直接照着配)。

---

## 零、先立坐标系:什么时候用哪个

| 手段 | 解决什么问题 | 什么时候上 |
|------|-------------|-----------|
| **主从 + 读写分离** | 读压力大、主库 CPU 扛不住 | **单表几十万到几百万**就考虑 |
| **分库** | 单库连接数/磁盘/写入瓶颈;业务隔离 | 单库撑不住、多业务混在一库 |
| **分表** | **单表数据量大、索引退化、查询变慢** | **单表过千万级**,是分表的重要信号 |

> **核心心法**:不是上来就分库分表!分库分表是**最后手段**,因为它带来巨大复杂度。
> 顺序应该是:**先优化 SQL/加索引 → 上缓存(Redis)→ 读写分离 → 分表 → 最后才分库**。

## 一、读写分离(承接第一篇,这里讲"怎么落地")

### 1.1 用商城订单举例子

```
用户查我的订单 ──► Slave(读)     ← 读操作走从库
用户提交订单   ──► Master(写)     ← 写操作走主库
```

目标:把读流量从主库卸到从库,主库专心写。**读多写少**(看的多买的少)的商城,收益巨大。

### 1.2 落地方式:中间件 vs 应用层

**方式一:中间件(ShardingSphere / MyCat)—— 推荐,透明无侵入**
程序连中间件,中间件按 SQL 判断是读是写,自动路由。

**方式二:应用层(Spring 动态数据源 + AOP)**
代码里给方法打注解,如 `@ReadOnly` → 走从库,否则走主库。

```java
// 方式二 示意(包名 com.example)
@ReadOnly            // 查订单,只读 → 路由到从库
public List<Order> listMyOrders(Long userId) {
    return orderMapper.selectByUserId(userId);
}

@Transactional       // 提交订单,写 → 路由到主库
public Long createOrder(Order order) {
    orderMapper.insert(order);
    return order.getId();
}
```

### 1.3 落地必踩两坑(面试加分)

1. **主从延迟**(第一篇讲过):强一致操作强读主,或用"刚写的 key 短暂读主"。
2. **事务内读写一致**:一个事务里先写后读,必须全程走主库,否则事务内读从库可能读不到自己刚写的。

## 二、分库分表是什么,为什么做

### 2.1 单表撑不住的信号(面试必问)

一张 **order 表**到了 **1000 万行** 之后:

- **B+ 树更高 → 查询 IO 增加 → 变慢**(就算有索引)。
- **锁竞争**:单表写入的锁开销随数据量增加。
- **单库写入瓶颈/连接数不够**。

分库分表 = **把一张大表拆成多张小表/多个库**,让每份变小、性能回升。

### 2.2 三种拆法(核心,必须分清)

| 拆法 | 大白话 | 例子(order 表) |
|------|--------|----------------|
| **垂直分表**(拆列) | 列太多,把**不常查的大字段/关联信息**拆到别的表 | order 主表(核心字段)+ order_detail(明细/大字段) |
| **垂直分库**(拆业务) | 一个库里塞了多个业务表,按**业务**拆到不同库 | 订单库 order_db、商品库 product_db、用户库 user_db |
| **水平分表 / 分库**(拆行) | 数据量太大,把**行**按规则分到多张表/多个库 | order_0、order_1、order_2...(按 userId 取模) |

> **面试重点**:垂直分库是"**按业务隔离**"(账户、订单、商品分开,各管各的);水平分表是"**把同一类海量数据拆开**"。这俩是不同维度,别搞混。

### 2.3 商城场景的典型拆分(讲出来很加分)

```
原单机:user/product/order 全在一库

垂直分库后:
  user_db   │  product_db │  order_db
  ─────────┼─────────────┼────────────
  user 表    │  product 表  │  order 表(仍很大)

order_db 里再水平分表(order 表过千万):
  order_db 的 order_0 / order_1 / ... / order_15(按 userId 取模 16)
```

## 三、分片键与路由规则(分库分表灵魂)

### 3.1 分片键(Sharding Key)怎么选(面试核心)

**分片键 = 按哪个字段来分**。选错直接翻车。

**商城的正确示范**:订单表用 **`user_id`** 做分片键(按用户分)。
- 因为用户查"**我的订单**"最频繁 → 一个用户的订单都在同一片 → 一次查询只打一片,快。

**反面教材(面试必踩点)**:
- 用 `order_id` 做主分片 → 查"某用户的所有订单"时,不知道订单在哪个片 → 得**全库全表广播**(去所有分片查一遍再合并)→ 慢死。
- 结论:**分片键要贴近最核心的查询维度**,通常是 shard 里用 **user_id / 商户 id / 客户 id** 这种"按某个体划分"的字段。

### 3.2 三种分片算法(背熟)

| 算法 | 规则 | 优点 | 缺点 |
|------|------|------|------|
| **取模/哈希** | `shardId = userId % 16` | 均匀、实现简单 | 扩容要重分(16→32 是灾难) |
| **范围(range)** | 按区间分(order_id 1-1000万片0,1000万-2000万片1) | 扩容好加 | 可能不均匀(热点集中在某片) |
| **一致性哈希/区间+哈希** | 解决扩容问题 | 扩容平滑 | 实现复杂 |

> **面试金句**:取模简单但**扩容难**(原来是 %16,想扩到 %32 所有数据位置全变);范围好扩容但**可能热点不均**。生产常用 **一致性哈希** 或 **范围+哈希结合** 平衡两者。

## 四、中间件:ShardingSphere(最流行的落地方式)

### 4.1 是什么

**ShardingSphere**(Apache 顶级项目)是一套"数据库中间件",帮你把上面那套**读写分离、分库分表**自动搞定,对业务代码尽量透明。分两种形态:

| 形态 | 大白话 |
|------|--------|
| **ShardingSphere-JDBC** | 拎包入住:引入依赖,应用直连多个库,自己路由(像数据源增强) |
| **ShardingSphere-Proxy** | 独立服务:当"代理数据库",应用连它,它转发到真正的库(像 MyCat) |

> 对 Java 项目,**ShardingSphere-JDBC** 更常用(无额外部署、性能好)。MyCat 是老牌,两者思路类似,面试提 ShardingSphere 更主流。

### 4.2 配置示例(yaml,占位符,可运行)

```yaml
# ShardingSphere 数据源配置(data-sources 命名接口,以 order 为例)
dataSources:
  ds_master:        # 主库(写)
    url: jdbc:mysql://your-master-host:3306/order_db
    username: your_user
    password: your-pass
  ds_slave_0:       # 从库(读)
    url: jdbc:mysql://your-slave0-host:3306/order_db
    username: your_user
    password: your-pass
  ds_slave_1:
    url: jdbc:mysql://your-slave1-host:3306/order_db
    username: your_user
    password: your-pass

rules:
  # ── 读写分离 ──
  - !READWRITE_SPLITTING
    dataSources:
      readwrite_ds:                 # 逻辑数据源名
        writeDataSourceName: ds_master
        readDataSourceNames:
          - ds_slave_0
          - ds_slave_1

  # ── 分表(把 order 表按 user_id 取模拆 16 片)──
  - !SHARDING
    tables:
      t_order:
        actualDataNodes: ds_master.t_order_${0..15}   # 实际落到哪张表
        tableStrategy:
          standard:
            shardingColumn: user_id                  # 分片键:按用户
            shardingAlgorithmName: order_inline

    shardingAlgorithms:
      order_inline:
        type: INLINE
        props:
          algorithm-expression: t_order_${user_id % 16}  # 取模 16
```

> ⚠️ 说明:上面是**配置形态示意**,帮你看懂结构。真正跑起来要 SpringBoot 依赖、逻辑库逻辑表命名(逻辑表和真实表的关系)、以及建好那 16 张物理表。文末"可运行示例"给最小工程思路。

## 五、分库分表的大坑(面试答不上的地方,背下来加分)

| 坑 | 大白话 | 对策 |
|----|--------|------|
| **跨分片 join 没了** | 表拆了,原来的 JOIN 跨片做不了 | 尽量避免 join;冗余存储/应用层合并/ES 搜索 |
| **分布式事务** | 跨库写操作不再是单库事务 | 引入可靠消息/事务消息/最终一致性方案 |
| **分布式 ID** | 自增主键在分片下会重复 | 改用雪花(Snowflake)算法、发号器 |
| **扩容灾难** | 取模分片想加机器要全量重分 | 一致性哈希、规划好初始分片数、索引设计 |
| **全局查询/聚合** | 分片后 count/统计要全片汇总 | ES/数仓/离线统计,别在库上硬算 |
| **数据迁移** | 老数据要搬到新分片 | 在线迁移工具、双写、灰度过流 |
| **主键/外键依赖** | 分片后外键约束基本放弃 | 应用层保证一致性 |

> **心法(面试总结句)**:分库分表不是免费午餐,它是用 **复杂度换性能**。拆之前一定要想清楚:查询维度、分片键、扩容方案、分布式事务怎么兜。**能不拆就不拆,要拆就一次性规划好分片规则(尤其预留扩容)**。

## 六、从单机到千万级演进路线图(全篇收尾彩蛋)

把整个 MySQL 治理串成一条路(面试讲这个特别清晰):

```
单机一台库
  │ 加索引 + 优化 SQL + 上 Redis 缓存
  ▼
主从复制(冗余,基础)
  │ 读压力大
  ▼
一主多从 + 读写分离(压读)
  │ 单表过千万 / 单库瓶颈
  ▼
垂直分库(按业务拆) + 水平分表(按 user_id 拆)
  │ 上中间件 ShardingSphere 透明化
  ▼
高可用兜底:Orchestrator/MGR 自动切换
  + 每天全量 + binlog 增量 + 异地副本(备份/容灾)
```

> **一句话总结整篇**:读写分离先解决"读的瓶颈",分库分表再解决"数据规模/写入的瓶颈",但每一步都引入新复杂度(延迟、事务、分布式 ID、扩容),所以**按需演进、别过度设计**。

## 七、面试突击速查

| 问题 | 一句话答法 |
|------|-----------|
| 什么时候该分表? | 单表过千万、索引退化、查询变慢 |
| 垂直 vs 水平? | 按列/按业务拆 vs 按行拆到多表库 |
| 分片键怎么选? | 贴近最频繁查询维度(商城用 user_id),避免全片广播 |
| 取模扩容难在哪? | %N 想变 %M 所有数据位置全变,建议一致性哈希/预留分片 |
| 跨分片 join 怎么办? | 尽量别 join:冗余、应用合并、上 ES/数仓 |
| 分布式事务? | 可靠消息+最终一致性,避免强一致双写 |
| 分库分表核心心态? | 用复杂度换性能,按需演进别过度设计 |
