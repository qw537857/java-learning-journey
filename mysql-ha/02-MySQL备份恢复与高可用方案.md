# 02 MySQL 备份恢复与完整高可用方案

- **日期**:2026-08-31
- **一句话总结**:高可用解决"机器挂了怎么办",备份解决"**数据丢了/坏了怎么找回来**"。本篇讲清楚备份的几种类型、怎么组合出"可以恢复任意时间点"的备份体系,以及怎么把备份和上一篇的高可用拼成完整方案,继续用商城订单系统打比方。
- **配套代码**:文末含 mysqldump 常用命令和恢复步骤(占位符)。

---

## 零、先理解:高可用 ≠ 备份(面试易混,必区分)

很多人把"主从复制"当成"备份",其实**大错特错**。这俩是两码事:

| | 主从/高可用 | 备份恢复 |
|---|------------|---------|
| 防的是 | **机器/进程挂了** | **数据丢了、坏了、删错了** |
| 丢数据时 | 主从同步可能会跟着丢(异步复制) | 能从备份里找回来 |
| 典型场景 | 主库宕机自动切换 | 误删一张表 / 运营商跑路 / 被攻击删库 |

> **血泪教训场景(背下来,面试讲出来特别有说服力)**:
> 商城运营手一抖 `DELETE FROM order WHERE ...` 少加了个条件 → 订单全删了。
> 这时候主从复制帮不上忙(从库也跟着"复制"了这次删除!)。**只有备份能救命。**
> 所以:高可用和备份**都要做**,而且主从复制本身**不能替代备份**。

## 一、备份的两种维度(先建立坐标系)

### 1.1 按"数据形态"分:逻辑备份 vs 物理备份

| 类型 | 大白话 | 存的是什么 | 优点 | 缺点 | 工具 |
|------|--------|-----------|------|------|------|
| **逻辑备份** | 把数据"翻译"成 SQL 语句导出 | INSERT/SQL 文本 | 跨版本、可读、恢复可控 | 慢、占空间 | **mysqldump** |
| **物理备份** | 直接复制数据文件(整个目录) | 数据文件本身 | 快、恢复快 | 依赖版本/平台 | **XtraBackup** |

> **面试一句话**:数据量小用 `mysqldump`(逻辑备份,简单);数据量大用 `XtraBackup`(物理备份,快,还支持在线备份不锁库)。

### 1.2 按"备份范围"分:全量 / 增量 / 差异

- **全量备份**:把整库全拷一份。最重,但最完整。适合小库或定期(如每天)。
- **增量备份**:只备份"上次备份之后新增/变化的部分"(靠 binlog)。轻,恢复时要先全量再逐个增量。
- **差异备份**:只备份"距上次全量备份"的变化。介于两者之间(不常用,主要理解全量 vs 增量的组合)。

> **组合拳(重点)**:**全量 + binlog 增量** 是业界标配。恢复时 = **全量恢复 + 重放 binlog 到指定时间点** → 这就是"**时间点恢复(PITR, Point-In-Time Recovery)**",能把数据恢复到**任意一秒**。

## 二、恢复的三种粒度(知道能恢复到多细)

| 粒度 | 大白话 | 场景 |
|------|--------|------|
| **整个实例恢复** | 整库/整机重来 | 机房挂了整机重建 |
| **单库/单表恢复** | 只捞出某个库/某张表 | "某某表数据坏了,重导一下" |
| **时间点恢复(PITR)** | 恢复到指定时刻 | 误删除,恢复到删除前那一刻 |

> 面试加分:**PITR 依赖 binlog**。所以生产必须开 binlog,理由之一就是为了能"回放"到任意时间点。

## 三、备份策略:怎么设计才靠谱(面试实战题)

**面试官常问:"给你一个商城系统,备份怎么设计?"** 可以这么答:

1. **全量**:每天凌晨跑一次 `mysqldump` 或 `XtraBackup` 全量备份(业务低峰期)。
2. **增量**:binlog 持续开启,实时/定时同步增量(或每天定时把 binlog 归档)。
3. **异地**:备份文件**复制一份放到异地/对象存储**(比如另一个机房、云桶),防机房级事故。
4. **保留策略**:按需保留(比如最近 7 天每天、最近 4 周每周、最近 12 个月每月)。
5. **定期演练**:**备份一定要定期做恢复演练**!否则"备份了但恢复不了"等于没备份。
6. **恢复目标**:定 **RPO(允许丢多少数据)** 和 **RTO(允许停多久)** —— 详见下节。

> **金句(面试必说)**:最怕的备份不是"没做",是"**做了但从没验证过能不能恢复**"。所以要**演练、演练、演练**。

## 四、两个核心指标:RPO 和 RTO(高可用+备份一起用的衡量标准)

这是面试高频,必须背清楚:

| 指标 | 全称 | 大白话 | 决定了什么 |
|------|------|--------|-----------|
| **RPO** | Recovery Point Objective | **允许丢失多少数据**(往前回退多久) | 备份多频繁、复制多严格 |
| **RTO** | Recovery Time Objective | **允许停机多久**才能恢复 | 切换/恢复速度要求 |

**商城系统的例子**:
- 想 RPO ≤ 5 分钟(最多丢 5 分钟数据)→ 备份/同步频率要很高(如每 5 分钟增量 + 半同步复制)。
- 想 RTO ≤ 10 分钟 → 自动切换、备库常驻、恢复流程自动化。

> 关系:高可用主要压 **RTO**(尽快恢复),备份主要保 **RPO**(尽量少丢)。两者配合才完整。

## 五、完整 MySQL 高可用方案(把一二篇串起来)

面试官问你"**你们的高可用方案怎么搭**",可以按这个框架答(以商城为例):

```
业务层
  │
  ▼
MySQL Router / 中间件  ←── 读写分离 + 故障感知
  │            │
  ▼            ▼
Master(主) ──binlog──► Slave1 / Slave2(从,扛读)
  │                    │
  │  Orchestrator / MGR 自动监控、自动切换(压 RTO)
  ▼
备份体系:每天全量 + binlog 增量 + 异地副本(保 RPO)
```

**要点清单(答完整方案就靠它)**:
1. **冗余**:一主两从,从库扛读(读写分离)。
2. **自动切换**:Orchestrator / MGR / Keepalived 监控主库,挂了自动提从为主(压 RTO)。
3. **数据保护**:每天全量备份 + binlog 增量 + 异地容灾副本(压 RPO)。
4. **监控告警**:延迟监控(Seconds_Behind_Master)、磁盘容量、主从健康状态。
5. **演练**:定期做故障切换演练和备份恢复演练。

## 六、常用命令速查(占位符,可运行)

```bash
# ── 逻辑备份(mysqldump)──
# 整库导出
mysqldump -u your_user -p your_db > your_db_backup.sql
# 只导出某张表
mysqldump -u your_user -p your_db your_table > your_table.sql
# 导出数据+建表结构,带时间点一致性的常用参数
mysqldump -u your_user -p --single-transaction --routines --triggers your_db > backup.sql

# ── 恢复 ──
mysql -u your_user -p your_db < your_db_backup.sql

# ── 查看 binlog 相关(确认增量备份基础有没有开)──
SHOW VARIABLES LIKE 'log_bin';
SHOW MASTER STATUS;              -- 当前 binlog 位置
SHOW BINARY LOGS;                -- 列出所有 binlog 文件
SHOW SLAVE STATUS\G              -- 看主从延迟:Seconds_Behind_Master
```

> ⚠️ 生产一般用 **XtraBackup**(物理、在线、不锁库)+ 空间大时配 binlog 增量。这里给 mysqldump 是为了"最小可运行、看得懂",生产落地请按公司规范。

## 七、面试突击速查

| 问题 | 一句话答法 |
|------|-----------|
| 主从复制算备份吗? | 不算,主从防"机器挂",备份防"数据丢",删库场景只有备份能救 |
| 逻辑备份 vs 物理备份? | SQL 导出 vs 文件拷贝,mysqldump vs XtraBackup |
| 什么是 PITR? | 时间点恢复,全量+binlog 回放到指定时刻 |
| RPO/RTO 差异? | 丢多少数据 / 停多久服务 |
| 最完整的备份方案? | 每天全量 + binlog 增量 + 异地副本 + 定期演练 |
