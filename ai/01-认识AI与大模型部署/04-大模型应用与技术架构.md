# 大模型应用:能力边界与技术架构(2026-09-08)

> 来源:AI 课程导图(03 大模型应用开发)整理,面向 Java 初级工程师。
> 目标:搞懂"传统程序 vs 大模型各自擅长什么、怎么强强联合",并掌握四种应用架构的选型思路(Prompt / Function Calling / RAG / Fine-tuning)。

---

## 一、传统应用 vs 大模型:各有所长

### 1.1 传统程序(Java 程序员最熟)

- **核心特点**:基于明确规则的逻辑,确定性执行、结果可预测。
- **擅长**:结构化计算(银行转账、Excel 公式)、确定性任务(排序算法)、高性能低延迟(数据库索引)、规则明确的流程控制(红绿灯)。
- **不擅长**:非结构化数据(看不懂自然语言"帮我写首秋天的诗")、模糊推理与模式识别(判断图里是猫还是狗)、动态适应性(需求天天变,代码要跟着改)。

### 1.2 AI 大模型

- **核心特点**:基于数据驱动的**概率推理**,擅长处理模糊性和不确定性。
- **擅长**:自然语言处理(写文章、翻译、客服意图识别)、非结构化数据分析(医学影像、语音转文字)、创造性内容生成(Stable Diffusion 画图、AI 作曲)、复杂模式预测(基于历史数据做趋势预测)。
- **不擅长**:精确计算(`12345 × 6789` 可能算错)、确定性逻辑校验(身份证号规则校验可能编出"看着合法其实非法"的号)、低资源场景(微波炉控制程序跑不起大模型)、**因果推理**(可能误判"公鸡打鸣导致日出")。

### 1.3 强强联合(Hybrid AI)= 大模型应用的真谛

```
传统编程:确定性、规则化、高性能 → 负责数学计算、流程控制、数据读写
AI 大模型:概率性、非结构化、泛化性 → 负责语言理解、内容生成、意图识别
```

经典落地:

- **智能客服**:AI 理解用户问题 → 传统代码查数据库返回准确结果;
- **增强可解释性**:规则引擎约束 AI 输出(法律文书强制符合条款格式);
- **低代码/无代码**:AI 自动生成代码(GitHub Copilot 这类)。

---

## 二、大模型 ≠ 大模型应用(务必分清)

- **大模型**(GPT、DeepSeek):只是"生成式模型"——根据前文续写 + 基础推理;
- **AI 对话产品**(ChatGPT、各家助手):除生成外还有**会话记忆、联网**等功能——这些大模型本身**不具备**,是**外面套的一层程序**实现的。

> 结论:我们天天用的 AI 产品,本质都是**基于大模型开发的应用**,不是大模型本身。

## 三、四种大模型应用技术架构(面试重点)

### 3.1 纯 Prompt 模式(最便宜)

- 不断雕琢提示词让大模型给出理想答案 = **提示词工程(Prompt Engineering)**;
- 很多简单 AI 应用,一段足够好的提示词就够了;
- 成本:最低,零开发量(除了写提示词)。

### 3.2 Function Calling(让 AI 能"调用工具")

**问题**:大模型懂自然语言,但**无法直接操作数据库、执行严格业务规则**。

**思路**:把传统应用的能力包装成函数,交给 AI 按需调用:

```
1. 把业务功能封装成一个"函数"(Function),并在提示词里描述清楚每个函数的作用
2. AI 理解用户意图,判断该调哪个函数、需要什么参数,把任务拆成步骤(这就是 Agent 雏形)
3. AI 返回"函数名 + 参数"(自己不执行)
4. 传统程序拿到后调用本地函数,把执行结果拼回提示词再发给 AI
5. 循环,直到完成目标
```

> ⚠️ 不是所有大模型都支持 Function Calling,**DeepSeek-R1 不支持**;选型时注意查文档。

### 3.3 RAG:检索增强生成(解决"知识不够新、不够专")

**大模型的知识限制**:

1. **时效性差**:训练数据是旧的,无法实时更新;
2. **缺专业领域知识**:训练数据是通用数据,缺少企业内部/专业内容。

**为什么不能把资料全拼进提示词?** 上下文窗口有限——早期 GPT3 只支持 2000 token,现在领先模型也不超过约 200K token,**海量知识库塞不进去**。

**RAG 思路**:用信息检索技术给大模型"外挂知识库":

```
检索模块(Retrieval):
  文本拆分:把知识文档拆成片段
  文本嵌入(Embedding):把片段向量化分类存储(向量库)
  文本检索:根据用户问题找出最相关的片段
生成模块(Generation):
  组合提示词:检索片段 + 用户问题 → 拼成丰富上下文
  生成结果:调用大模型基于知识库内容回答
```

> 妙处:每次只取"与问题相关的片段"而不是整个知识库,既不超过上下文限制,又保证回答基于企业知识库。

### 3.4 Fine-tuning:模型微调(最贵)

- 在预训练大模型(DeepSeek/Qwen)基础上,**用企业自己的数据继续训练**,让回答更贴合业务;
- 通常保留模型大部分结构参数,只调整一小部分——利用已有知识,减少训练时间和算力;
- 步骤:选预训练模型 → 准备领域数据集 → 调超参数(学习率/批次/轮次)→ 训练优化(前向传播/损失/反向传播/权重更新);
- 缺点:需要大量算力、调参复杂、有过拟合风险——**成本高难度大,不适合大多数企业**。

---

## 四、技术选型(原则记牢)

```
开发成本从低到高:Prompt < Function Calling < RAG < Fine-tuning
```

**选型首要原则:在达成目标效果的前提下,尽量降低开发成本。**

- 简单问答 → 先试纯 Prompt;
- 需要操作数据库/业务 → Function Calling;
- 需要回答"最新/专业知识库内容" → RAG(企业落地最常见);
- 要模型"变成行业专家级"且有预算 → 才考虑微调。

---

## 五、本节速记

| 架构 | 一句话 | 成本 |
|------|--------|------|
| 纯 Prompt | 提示词工程,零代码 | 最低 |
| Function Calling | AI 理解意图→返回函数名参数→程序执行 | 低 |
| RAG | 向量检索外挂知识库,解决时效与领域知识 | 中 |
| Fine-tuning | 用自己的数据继续训练模型 | 最高 |
