## 一、并发编程中的三个问题

| 问题 | 含义 | 例子 |
|------|------|------|
| **可见性** | 一个线程改共享变量,另一个线程不能立即看到最新值 | 变量只改了线程工作内存,没同步回主内存 |
| **原子性** | 一次或多次操作**要么全部执行、要么全不执行**,不被其他因素中断 | `number++` 在指令级不是原子的(见下) |
| **有序性** | 编译器/CPU 会优化重排代码,执行顺序 ≠ 编写顺序 | 指令重排序 |

验证 `number++` 非原子(javap 反编译):

```
javap -p -v Test02Atomicity.class

9:  getstatic   #18   // Field number:I
12: iconst_1
13: iadd
14: putstatic   #18   // Field number:I
```

> 一条 `number++` 在指令层是"读 → 加 → 写"三步,两个线程交错执行就会丢更新。
> 压测工具:OpenJDK **jcstress**(https://wiki.openjdk.java.net/display/CodeTools/jcstress),专门做并发正确性压力测试。

## 二、Java 内存模型(JMM)

### 2.1 先看计算机硬件结构

- **CPU**:程序最终变成指令由 CPU 执行;运算速度极快;
- **内存(主存)**:程序运行时的数据存放处;CPU 访问内存很慢;
- **缓存**:为了弥补"CPU 快、内存慢",CPU 和主存之间加缓存。

**CPU Cache 三级结构**:离 CPU 越近越快、容量越小。

| 级别 | 容量(示例) | 归属 |
|------|-----------|------|
| L1 | 32K,最快 | 每个核独有 |
| L2 | 256K | 每个核独有 |
| L3 | 12MB,最慢 | 同一 CPU 插槽的核共享 |

访问过程:CPU 先找 L1 → 没命中找 L2 → L3 → 主存 → 硬盘;算完再把最新数据刷新回主存。

### 2.2 JMM 是什么

- Java 内存模型 = **一套规范**,屏蔽底层不同计算机的差异;
- 它描述了共享变量的访问规则(变量怎么存内存、怎么从内存读)。

**两个关键区域:**

| 区域 | 说明 |
|------|------|
| 主内存 | 所有线程共享,所有共享变量存在这里 |
| 工作内存 | 每个线程独有,保存共享变量的**副本**;线程读写都必须在自己的工作内存完成,不能直接读写主内存;线程之间也不能直接访问对方工作内存 |

> JMM 与硬件的关系:JMM 的"主内存/工作内存"是**抽象概念**,实际数据都物理存在于主存/CPU 缓存/寄存器中——两者是"抽象规则"与"物理硬件"的交叉关系。

### 2.3 主内存与工作内存的交互:8 种原子操作

```
lock → read → load → use → assign → store → write → unlock
```

| 操作 | 作用 |
|------|------|
| lock | 锁定主内存变量(独占) |
| read | 从主内存读取变量 |
| load | 把 read 的值载入工作内存副本 |
| use | 工作内存变量交给执行引擎使用 |
| assign | 执行引擎结果赋给工作内存变量 |
| store | 把工作内存变量传回主内存 |
| write | 把 store 的值写入主内存变量 |
| unlock | 解锁(前提:先把变量同步回主内存) |

**注意两条**:① 对变量执行 lock 会**清空工作内存中该变量的值**;② unlock 之前**必须先同步回主内存**——这正是 synchronized 保证可见性的根基。

## 三、synchronized 如何保证三大特性

| 特性 | synchronized 怎么保证 |
|------|----------------------|
| 可见性 | 锁释放前强制把工作内存变量刷回主内存(unlock 前置 write);获取锁时清空工作内存重新 read |
| 原子性 | 锁让临界区同一时刻只有一个线程执行,天然互斥 |
| 有序性 | 加锁/解锁有明确顺序;且锁内代码不会跟锁外乱重排 |

### 3.1 关于重排序的两个概念

- **为什么要重排**:编译器、CPU 为了提高执行效率;
- **as-if-serial**:不管怎么重排,**单线程结果必须正确**。

```
不可重排(有依赖):          可以重排(无依赖):
int a = 1;                 int a = 1;
int b = a;   ← 写后读      int b = 2;
int a = 2;   ← 写后写      int c = a + b;
int a = 1;                 // 可以变成
int b = a;   ← 读后写      int b = 2;
int a = 2;                 int a = 1;
                           int c = a + b;
```

## 四、synchronized 的特性

### 4.1 可重入

- **定义**:同一个线程可以多次执行 synchronized,**重复获取同一把锁**;
- **原理**:锁对象里有个计数器(recursions),记录线程拿了几次锁,每次进入 +1、退出 -1;
- **好处**:① 避免死锁(自己不会把自己锁死);② 方便封装代码(方法 A 调方法 B,两个都加锁没问题)。

### 4.2 不可中断

线程拿不到锁就**一直阻塞/等待**,除非持锁线程主动释放,不能被中断。

## 五、synchronized 的底层原理

### 5.1 同步代码块:monitorenter / monitorexit

反编译后,synchronized 代码块对应两条字节码指令:

- **monitorenter**:尝试获取对象关联的 **monitor(监视器)** 的所有权;
- **monitorexit**:释放 monitor 所有权。

monitor 的规则(JVM 规范原文翻译):

```
monitorenter:
1. monitor 进入数为 0 → 线程进入,进入数置 1,该线程成为 owner
2. 线程已拥有该 monitor → 重入,进入数 +1
3. 其他线程已占用 → 阻塞等待,直到进入数为 0 再重新竞争

monitorexit:
1. 能执行该指令的线程一定是当前 monitor 的 owner
2. 进入数 -1;减到 0 → 退出 monitor,不再拥有所有权,唤醒阻塞线程竞争
```

### 5.2 同步方法:ACC_SYNCHRONIZED

- 同步方法在字节码层面加 **ACC_SYNCHRONIZED** 标志;
- JVM 调用该方法时**隐式执行 monitorenter**,方法结束(含异常)时自动 **monitorexit**;
- 异常也不用担心:即使方法抛异常,JVM 也会在异常抛出前自动释放 monitor。

> 速记:每个对象都关联一个 monitor,monitor 有 owner 和进入数——**这就是锁的本质**。

### 5.3 面试题:synchronized 与 Lock 的区别

| # | synchronized | Lock |
|---|--------------|------|
| 1 | 关键字 | 接口(如 ReentrantLock) |
| 2 | 自动释放锁 | **必须手动释放**(finally 里 unlock) |
| 3 | 不可中断 | 可中断,也可不中断 |
| 4 | 无法知道是否拿到锁 | 能通过 tryLock 知道 |
| 5 | 能锁方法、锁代码块 | 只能锁代码块 |
| 6 | 非公平锁 | ReentrantLock 可控制公平/非公平 |

## 六、JDK6 对 synchronized 的优化

### 6.1 为什么老的 synchronized 慢?(重量级锁的代价)

- 没竞争到锁的线程会被 **park() 挂起**,拿到锁的被 **unpark() 唤醒**;
- 挂起/唤醒涉及**操作系统用户态 ↔ 内核态切换**,传递变量多、还要保护寄存器现场,**消耗大量系统资源**;
- 所以传统 synchronized 被称为"重量级锁"。

> 用户态:上层应用运行的状态;内核态:进程调用系统调用(如 I/O)陷入内核运行的状态。切换开销大。

### 6.2 CAS(Compare And Swap)

- **是什么**:CPU 提供的一条特殊指令,把"比较 + 交换"变成**原子操作**;
- **三个值**:内存值 V、旧预估值 X、要写的新值 B——只有当 `V == X` 时才把 B 写入 V;
- **保证**:共享变量赋值的原子性由 CPU 保证。

| 锁思想 | 做法 | 代表 |
|--------|------|------|
| 悲观锁 | 每次拿数据都认为别人会改 → 先上锁,别人阻塞 | synchronized、ReentrantLock |
| 乐观锁 | 认为别人不会改 → 不上锁,更新时发现被改了再重试 | CAS |

CAS 要点:变量用 **volatile** 保证可见性;CAS + volatile = 无锁并发,适合**竞争不激烈、多核**场景;竞争激烈时重试频繁,效率反而下降。

### 6.3 锁升级:无锁 → 偏向锁 → 轻量级锁 → 重量级锁

JDK6 后 synchronized 不再是"一上来就重量级",而是根据竞争程度**逐级升级(不可逆)**。

#### 对象在内存中的布局(前置知识)

对象 = **对象头 + 实例数据 + 对齐填充**。

- **对象头**:
  - **Mark Word**:存运行时数据——hashCode、GC 分代年龄、**锁状态标志**、持有锁的线程 ID、偏向时间戳等(32 位/64 位机器长度不同);
  - **klass pointer**:类型指针,指向类元数据(JVM 靠它知道对象是哪个类的实例;64 位可用 `-XX:+UseCompressedOops` 开指针压缩省内存);
- **实例数据**:类里定义的成员变量;
- **对齐填充**:HotSpot 要求对象起始地址是 8 字节整数倍,不够就补位。

用 JOL 看对象布局:

```xml
<dependency>
    <groupId>org.openjdk.jol</groupId>
    <artifactId>jol-core</artifactId>
    <version>0.9</version>
</dependency>
```

```java
System.out.println(ClassLayout.parseInstance(p).toPrintable());
```

> **锁存在哪?** 就存在锁对象的 **Mark Word** 里(锁标志位 + 线程 ID 等)。

#### ① 偏向锁(只有一个线程反复拿锁)

- 背景:大多数情况下锁**不存在竞争,总被同一线程获取**,为降低获取锁的代价引入;
- 原理:第一次获取时把标志位置"01(偏向模式)",用 CAS 把**线程 ID 写进 Mark Word**;之后该线程进出同步块只检查标志位和 ThreadID,**不再做任何同步操作**;
- 撤销:必须等到**全局安全点**,暂停持有线程,判断锁对象是否被锁定,再撤销回无锁(01)或升级为轻量级锁(00);
- 参数:`-XX:BiasedLockingStartupDelay=0` 关掉启动延迟(默认启动几秒后才激活);`-XX:-UseBiasedLocking` 直接关闭偏向锁;
- 注意:如果锁经常被多个线程访问(如线程池场景),偏向模式就是多余的。

#### ② 轻量级锁(多线程交替执行)

- 背景:多线程**交替**执行同步块,没有真正竞争,避免重量级锁开销;注意它不是替代重量级锁;
- 获取:
  1. 判断对象是否无锁(状态 01)→ 在当前线程**栈帧中建 Lock Record(锁记录)**,把 Mark Word 拷贝进去(这份拷贝叫 Displaced Mark Word),owner 指向锁对象;
  2. CAS 尝试把对象 Mark Word 更新为指向 Lock Record 的指针 → 成功则锁标志位变 **00**,执行同步代码;
  3. 失败 → 判断 Mark Word 是否已指向本线程栈帧(重入?直接执行);否则说明被别的线程抢了 → **膨胀为重量级锁**(标志位 **10**),后续线程阻塞;
- 释放:CAS 把 Displaced Mark Word 换回对象头;失败说明有竞争 → 膨胀升级;
- 本质:性能依据是"绝大部分锁整个生命周期无竞争";一旦真有竞争,比重量级锁还慢(互斥 + 额外 CAS)。

#### ③ 自旋锁(拿不到锁就"原地转圈"等一会)

- 背景:线程阻塞/唤醒要用户态↔内核态切换,代价大;而很多锁**只被占用很短时间**,不值得立刻挂起;
- 做法:让请求锁的线程执行**忙循环(自旋)**等一小会,不放弃 CPU,看持锁线程是否马上释放;
- 历史:JDK 1.4.2 引入(默认关,`-XX:+UseSpinning` 开),JDK6 默认开启;
- 默认自旋 10 次(`-XX:PreBlockSpin` 可改),超限还是挂起——自旋占 CPU,锁占用时间长时自旋是浪费;
- **适应性自旋锁(JDK6)**:自旋时间不固定了,由"前一次同一把锁的自旋结果 + 持锁线程状态"决定——上次成功就多等会(如 100 次),很少成功就干脆不自旋。虚拟机越跑越"聪明"。

#### ④ 锁消除 / 锁粗化(JIT 层优化)

- **锁消除**:JIT 检测到某段同步代码**不可能有共享数据竞争**(如局部变量加锁),直接把锁消除;
- **锁粗化**:一连串细碎操作都在对同一对象加锁,把同步范围**放大到整串操作外面**,只加一次锁。

### 6.4 编码层面的优化建议

1. **减少 synchronized 范围**:同步块尽量短,减少持锁时间、减少竞争;
2. **降低锁粒度**:一个大锁拆成多个小锁提高并发度(如 HashTable → ConcurrentHashMap,锁整表 → 锁分段/节点);
3. **读写分离**:读不加锁,写/删加锁(ConcurrentHashMap、CopyOnWriteArrayList、CopyOnWriteArraySet)。

## 七、本节速记

1. 并发三大问题:**可见性、原子性、有序性**,synchronized 三个都管;
2. JMM:共享变量在主内存,线程操作在工作内存副本,靠 8 种原子操作交互;
3. 锁本质:**每个对象关联一个 monitor(owner + 进入数)**,monitorenter 进、monitorexit 出;
4. synchronized vs Lock:自动释放 vs 手动释放、不可中断 vs 可中断、非公平 vs 可公平;
5. 锁升级:**无锁 → 偏向锁 → 轻量级锁 → 重量级锁**,锁信息存在对象头 Mark Word;
6. 慢的根源:阻塞唤醒要**用户态↔内核态切换** → 所以才有一层层优化(偏向/CAS/自旋)。
